Arquitetura é custo de mudança

Bloco 1 · Tópico 1

O que arquitetura não é

Não é diagrama bonito. Não é lista de tecnologias.

É o conjunto de decisões difíceis de reverter, e como elas afetam o custo de mudar o sistema.

A consequência incômoda

Um monólito com módulos bem separados pode ser mais fácil de evoluir do que microsserviços que compartilham banco e se chamam em cadeia.

A pergunta útil não é “qual padrão usar?”, e sim:

o que precisa ser fácil de mudar nos próximos dois anos?

O emaranhado

Bloco 1 · Tópico 2

Big Ball of Mud

Foote e Yoder, 1997: o padrão arquitetural mais comum da indústria.

  • Sem estrutura perceptível
  • Quase tudo depende de quase tudo
  • Nasce de decisões locais razoáveis, sob pressão, por anos

O artigo trata isso como realidade, não como vergonha.

O primeiro nível de maturidade

Reconhecer o emaranhado e isolá-lo. Sem reescrever tudo.

  1. Achar duas ou três áreas que mudam juntas
  2. Criar fronteira explícita entre elas
  3. Restringir o acesso aos dados ao próprio módulo

Ache a fronteira

Mini desafio 2 · 5 min

  • faturamento/ e contratos/ mudam juntos em 80% dos commits
  • relatorios/ quase nunca muda com os outros
  • usuarios/ aparece em commits de todos

O que isso diz sobre as fronteiras? Por onde começar?

Monólito modular

Bloco 1 · Tópico 3

Uma unidade de implantação

src/
  pedidos/       # regras e API pública do módulo
  pagamentos/    # só expõe PagamentoService e eventos
  estoque/
  shared/        # tipos e utilitários sem regra de negócio

A regra que faz a diferença

Cada módulo tem suas tabelas, e nenhum outro as consulta diretamente

Esse nível resolve a maioria dos problemas de equipes de tamanho médio — e costuma ser subestimado.

A fronteira só existe se o CI aplica

'no-restricted-imports': ['error', {
  patterns: [{
    group: ['**/pedidos/infra/*', '**/pagamentos/infra/*'],
    message: 'Importe apenas a API pública do módulo.',
  }],
}]

Em PHP, o equivalente é o Deptrac.

A fronteira foi violada

Mini desafio 3 · 5 min 

// src/pagamentos/CobrancaService.ts
import { PedidoRepository } from '../pedidos/infra/PedidoRepository';

Qual regra foi violada? Reescreva usando a API pública.

Quando microsserviços valem a pena

Bloco 2 · Tópico 4

O ganho é independência

Cada serviço tem processo, ciclo de release e, idealmente, banco próprios.

Pagamentos publica sem coordenar com catálogo. Um serviço escala sozinho.

O custo é igualmente real

  • Chamadas de rede falham; a latência se acumula
  • A consistência deixa de ser automática
  • O diagnóstico exige rastreamento distribuído

E cada serviço exige pipeline, monitoramento, plantão e documentação. O Módulo 3 inteiro, multiplicado.

Os três fatores

Fator Pergunta
Equipes Há menos de 3 ou 4 no mesmo código? Então modular basta
Escala / isolamento Alguma parte precisa escalar muito diferente?
Maturidade operacional Sem pipeline e observabilidade, amplifica o caos

Richardson para APIs

Bloco 2 · Tópico 6 · Extra

Quatro níveis

Nível O que é
0 Um endpoint só, geralmente POST, recebe e devolve tudo
1 Recursos com URLs próprias (/pedidos/42)
2 Verbos e códigos corretos; 201 com Location
3 Hipermídia: a resposta traz links das ações possíveis

Nível 2, na prática

POST /pedidos HTTP/1.1
Content-Type: application/json

{"itens": [{"sku": "LIV-1", "quantidade": 2}]}

HTTP/1.1 201 Created
Location: /pedidos/9187

Não é uma escada

O nível 3 não é sempre melhor

Uma API de nível 2 bem feita, com contrato claro, basta para a maioria dos casos.

Em que nível está

Mini desafio 6 · 7 min

  1. POST /api com {"acao": "criarPedido"}, sempre 200
  2. GET /pedidos/42 · POST /pedidos → 201 + Location
  3. Como a 2, mas com "_links" na resposta

Classificar e justificar

Desafio integrador · 45 min

Em dupla

Quatro sistemas

  1. Clínica: 40 usuários internos, equipe de quatro, carga estável
  2. Marketplace: quatro equipes com release próprio, picos sazonais
  3. Faturamento legado: módulos acessando o banco entre si, sem testes, duas pessoas
  4. API de CEP: alto volume de leitura, um único tipo de recurso

A regra de ouro

A justificativa precisa citar um fator do enunciado

“Escala melhor” não vale. “Quatro equipes com ciclos de release próprios” vale.

Fechamento

  • Arquitetura: decisões difíceis de reverter, medidas pelo custo de mudar
  • Emaranhado: o padrão mais comum; isole, não reescreva
  • Modular: tabelas próprias, API pública, fronteira no CI
  • Microsserviços: três fatores, não moda
  • Decisão sem registro é decisão que será refeita
