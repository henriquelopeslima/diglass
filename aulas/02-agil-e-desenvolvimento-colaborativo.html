O que muda entre Cascata e Ágil é quando o cliente vê o resultado e qual é o custo de errar.

Cascata

  • Fases em sequência: uma só começa quando a anterior termina
  • Cliente vê o software no fim
  • Funciona quando o requisito é estável e mudar é caro

Risco: descobrir o erro só na entrega.

Iterativo, incremental e XP

  • Iterativo: repete o ciclo, cada volta melhora a anterior
  • Incremental: entrega em partes que já funcionam
  • XP: práticas técnicas: TDD, pair programming, integração contínua, releases pequenos

Feedback cedo reduz o custo de errar.

Ágil

  • Pessoas acima de processos e ferramentas
  • Software funcionando acima de documentação
  • Colaboração acima de contratos
  • Mudanças acima de seguir um plano

Ágil não é “sem planejamento”.

Comparando

Modelo Entrega Mudança Bom para
Cascata No fim Cara Requisito fixo
Iterativo Por ciclo Média Produto que evolui
Ágil Contínua Esperada Requisito incerto

Scrum e Kanban

Bloco 1 · Tópico 2

Scrum em uma tela

Papéis Artefatos Eventos
Product Owner Product Backlog Sprint Planning
Scrum Master Sprint Backlog Daily
Time de Dev Incremento Review e Retrospectiva

Papéis

  • Product Owner: decide o quê e por quê; dono do backlog
  • Scrum Master: facilita o processo e remove obstáculos
  • Time de Dev: decide como e entrega o incremento

Artefatos e Definition of Done

  • Product Backlog: tudo o que pode ser feito, ordenado
  • Sprint Backlog: o que o time se compromete a fazer na sprint
  • Incremento: software funcionando ao fim da sprint

Definition of Done: o acordo do que significa “pronto”.

Cerimônias

Cerimônia Quando Duração
Daily Início de alguns encontros 5 min
Sprint Planning A cada 2 semanas 20 min
Review Ao entregar parte do projeto 15 min
Retrospectiva Fim de cada bloco 10 min

Kanban vs Scrum

Scrum Kanban
Ritmo Sprints fixas Fluxo contínuo
Escopo Fechado na sprint Muda a qualquer hora
Controle Capacidade da sprint Limite de WIP

Muitos times usam os dois: é o “Scrumban”.

História de usuário

Como <tipo de usuário>,
quero <fazer algo>,
para <obter um benefício>.

Critérios de aceite: como saber que está pronta.

Ex.: dado um pedido pago, quando consultar, então vejo o status.

Story points

  • Medem esforço relativo, não horas
  • Sequência típica: 1 · 2 · 3 · 5 · 8 · 13
  • Estima-se em grupo (planning poker)
  • Discordou? Converse: a discussão é o valor

GitHub Projects

Bloco 1 · Tópico 3

O board

Backlog → To Do → Doing → Review → Done

  • Backlog: ideias ordenadas
  • Doing: no máximo 1 ou 2 por pessoa
  • Review: PR aberto, aguardando revisão

Issue bem escrita

## Contexto
Por que isso importa.

## O que fazer
- [ ] Passo 1
- [ ] Passo 2

## Critérios de aceite
- [ ] Resultado observável

Organização

  • Labels: feature, bug, docs, tech-debt
  • Assignee: quem faz
  • Milestone: a sprint ou entrega
  • Closes #12 no PR fecha a issue no merge

Tarefa boa cabe em até 1 dia de trabalho.

Monte o board

Mini desafio 3 · 7 min

  1. Crie um GitHub Project (Board) no seu repositório
  2. Crie as colunas Backlog, To Do, Doing, Review, Done
  3. Adicione 3 issues com critério de aceite

Extra: crie os labels e um milestone “Sprint 1”.

Código padronizado

Bloco 2 · Tópico 4

Por que padronizar

O time precisa ler o código do outro sem esforço.

  • Estilo é decidido uma vez, pelo time
  • A ferramenta faz cumprir, não a revisão

Clean Code na prática

  • Nomes que revelam a intenção
  • Funções pequenas, com um só propósito
  • Sem repetição e sem números mágicos
  • Menos complexidade: caminho feliz claro

Nomes: antes e depois

function calc($a, $b, $t) { /* ... */ }
function calculate(int $a, int $b, string $operation): int

O segundo se lê sem abrir o corpo da função.

Padrões por linguagem

PHP JS / TS
Estilo PSR-12 Airbnb + Prettier
Estrutura PSR-4 (autoload) Módulos ES
Linter phpcs, php-cs-fixer ESLint

charset = utf-8

insert_final_newline = true
indent_style = space
indent_size = 4

[*.{js,ts,json,yml}]
indent_size = 2

Git, commits e PRs

O fluxo

→

→
[03] Push
→
[04] PR
→
[05] Review
→
[06] Merge
↺ o merge integra na main · sincronize e parta para a próxima branch
Nunca commite direto na main
O fluxo garante isolamento no desenvolvimento, visibilidade no PR e qualidade no code review antes da integração.

Conventional Commits

tipo(escopo): descrição no imperativo

feat(api): adiciona rota /health
fix(nginx): corrige proxy_pass do serviço app
docs: explica como rodar com docker compose

Tipos: feat · fix · docs · refactor · test · chore

Commit bom e commit ruim

Ruim Bom
fix stuff fix(api): retorna 404 quando pedido não existe
alterações docs: descreve variáveis do .env.example
wip refactor: extrai cálculo de desconto

PR de qualidade

## O que mudou
Adiciona a rota /health.

## Por quê
Necessária para o healthcheck do Compose.

## Como testar
`curl localhost:8080/health`

Closes #12

PR pequeno vence

  • Até ~300 linhas alteradas por PR
  • Um PR, um assunto
  • PR grande espera dias; PR pequeno sai em horas
  • Revise você mesmo antes de pedir review

Code review

Bloco 2 · Tópico 6

Para que serve

  • Aprender com o código dos outros
  • Padronizar o time
  • Prevenir bugs antes da produção
  • Nivelar o conhecimento do time

Não é competição. Não é julgamento de pessoa.

Autor e revisor

  • Autor: PR pequeno, descrição clara, autorrevisão antes
  • Revisor: comenta o código, não a pessoa
  • Ambos: respondem rápido e com respeito

Discutir estilo? Isso é trabalho do linter.

Como escrever o comentário

Ruim Bom
“Isso está errado.” “Aqui $id vai direto na query: risco de SQL injection. Use prepared statement.”
“Por que fez assim?” “Dúvida: por que não reutilizar calculateTotal()?”

Tipos de comentário

  • Bloqueante: precisa mudar antes do merge
  • Sugestão: melhora, mas pode ficar
  • Dúvida: quero entender
  • Elogio: ficou bom, diga também

Aprove quando o código melhora o sistema, mesmo sem ser perfeito.
