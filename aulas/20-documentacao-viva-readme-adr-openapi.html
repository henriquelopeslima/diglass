Documentação como código

Bloco 1 · Tópico 1

Por que ela falha

É escrita num lugar que o código não obriga ninguém a atualizar

Um wiki separado do repositório envelhece no dia seguinte à publicação.

A alternativa que funciona

  • Mesmo repositório
  • Revisão em PR
  • Verificada pelo pipeline

Documente o que o código não diz

  • Por que a arquitetura é assim
  • Como colocar o sistema no ar
  • Qual o contrato com os outros serviços
  • O que acontece quando algo falha

O que o código já diz claramente não precisa ser repetido em prosa.

Recebe pedidos da loja, valida estoque e publica `PedidoConfirmado`.

## Rodando localmente
Requer Docker e Node 20.

    cp .env.example .env
    docker compose up -d
    npm ci && npm run dev

    npm test                 # unitários
    npm run test:integracao  # exige o docker compose no ar

O teste do README

Siga-o literalmente, numa máquina limpa.

Cada passo que exige conhecimento tácito é uma falha do documento

E a correção é escrever o passo.

ADR no fluxo de PR

Bloco 1 · Tópico 3

A rotina, não o formato

  1. Decisão proposta → ADR escrito com status proposto
  2. A discussão acontece na PR
  3. A aprovação muda o status para aceito

A decisão e a documentação dela passam pela mesma revisão.

Contratos com OpenAPI

Bloco 2 · Tópico 4

Sem contrato explícito

Frontend, aplicativo e parceiros descobrem o formato por tentativa e erro.

A mudança de um campo quebra alguém sem aviso.

OpenAPI 3.1

paths:
  /pedidos/{id}:
    get:
      responses:
        "200":
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Pedido" }
        "404":
          description: Pedido não existe ou não pertence ao usuário
components:
  schemas:
    Pedido:
      type: object
      required: [id, status, total]
      properties:
        status: { type: string, enum: [aberto, pago, cancelado] }
        total:  { type: number, minimum: 0 }

O 404 é uma decisão de segurança

“Pedido não existe ou não pertence ao usuário”

Não revela se o recurso existe para outra pessoa.

É a decisão 403-vs-404 do E16, agora documentada no contrato.

Documente os erros

O contrato existe principalmente para os erros

O caminho feliz todo mundo adivinha.

Validar no pipeline

Bloco 2 · Tópico 5

Contrato não verificado vira ficção

Camada 1 — lint do arquivo:

npx @stoplight/spectral-cli lint openapi.yaml

Estilo e consistência: toda resposta de erro usa o mesmo schema?

Camada 2 — contra o comportamento real

schemathesis run openapi.yaml --base-url http://localhost:3000

Gera casos a partir do próprio contrato e executa contra a API.

Encontra divergências que teste escrito à mão deixa passar.

O contrato mente

Mini desafio 5 · 5 min

O contrato declara total como number, minimum: 0. O servidor respondeu total: null para um pedido cancelado.

Quem está errado? Que informação falta para decidir?

Code-first ou contract-first

Bloco 2 · Tópico 6 · Extra

As duas abordagens

Contract-first Code-first
Como Contrato antes do código Gerado do código
Vantagem Design discutido antes; consumidores em paralelo Menos manutenção
Risco Exige disciplina Expõe detalhe interno; contrato desenhado pelo código

Na prática, híbrido

O contrato é o artefato revisado, e a verificação automática garante que o código o cumpre.

O que não pode é ter dois documentos divergindo sem ninguém perceber

Qual abordagem

Mini desafio 6 · 7 min

  1. API nova, frontend desenvolvido em paralelo por outra equipe
  2. Serviço maduro, 60 endpoints, nenhuma documentação
  3. API pública com parceiros sob contrato comercial

Recomende para cada um.
