Cache

Bloco 1 · Tópico 2

Cache-aside

async function obterProduto(id: string): Promise<Produto> {
  const chave = `produto:${id}`;
  const cacheado = await cache.get(chave);
  if (cacheado) return JSON.parse(cacheado);

  const produto = await repo.buscarProduto(id);
  await cache.set(chave, JSON.stringify(produto), { EX: 300 });
  return produto;
}

As três perguntas

  1. Tolerância à desatualização — o preço pode estar 5 min atrás; o saldo na hora da compra, não
  2. Invalidação — TTL é o caminho mais simples
  3. Stampede — a chave quente expira e milhares vão ao banco juntas

Contra o stampede

  • TTL com variação aleatória
  • Bloqueio: só uma requisição recalcula
  • Atualização antecipada, antes de expirar
const ttl = 300 + Math.floor(Math.random() * 60);

O aviso do tópico

Cache não corrige consulta lenta

Ele esconde o problema enquanto a chave está quente — e o problema volta na primeira falta.

Filas

Bloco 1 · Tópico 3

Desacoplar e suavizar picos

Mil pedidos chegam num minuto. O serviço de e-mail processa cem por minuto.

A fila guarda a diferença: o e-mail atrasa, mas não se perde.

Três conceitos

  • Backpressure: o consumidor sinaliza que não aguenta. Fila sem limite é falha adiada.
  • Idempotência: entregas são pelo menos uma vez
  • Dead letter queue: a mensagem problemática sai, em vez de travar a fila

O erro mais caro

async function processar(msg) {
  await gateway.cobrar(msg.pedidoId, msg.valor, {
    idempotencyKey: `cobranca:${msg.pedidoId}`,
  });
  await repo.marcarComoPago(msg.pedidoId);
}

Sem a chave, uma retentativa após timeout cobra duas vezes.

Índices e EXPLAIN

Bloco 2 · Tópico 4

O banco é o gargalo

EXPLAIN ANALYZE
SELECT id, status, total FROM pedidos
WHERE cliente_id = 42
ORDER BY criado_em DESC
LIMIT 10;

O plano denuncia

Limit  (cost=18452.31..18452.33 rows=10)
  ->  Sort  (cost=18452.31..18463.88 rows=4628)
        Sort Key: criado_em DESC
        ->  Seq Scan on pedidos  (cost=0.00..18352.00 rows=4628)
              Filter: (cliente_id = 42)
              Rows Removed by Filter: 495372

Dois problemas: varredura sequencial e ordenação.

O índice composto

CREATE INDEX idx_pedidos_cliente_data
  ON pedidos (cliente_id, criado_em DESC);

Filtro primeiro, ordenação depois.

Índice só em cliente_id tira o Seq Scan e mantém o Sort.

Índice tem custo

Acelera leitura · encarece escrita · ocupa espaço

Índice que nenhuma consulta usa é só custo

Paginação e N+1

Bloco 2 · Tópico 5

OFFSET fica lento

SELECT * FROM pedidos
ORDER BY criado_em DESC
LIMIT 20 OFFSET 20000;

O banco percorre e descarta 20.000 linhas antes de devolver.

Página 1 instantânea, página 1.000 lenta — e em dev só existem três páginas.

Cursor: custo constante

SELECT * FROM pedidos
WHERE (criado_em, id) < ('2026-03-02 14:31:00', 'abc-123')
ORDER BY criado_em DESC, id DESC
LIMIT 20;

O desempate pelo id evita o bug de fronteira entre páginas.

Escalar

Bloco 2 · Tópico 6 · Extra

Vertical e horizontal

  • Vertical: máquina maior. Simples, e tem limite
  • Horizontal: mais instâncias. Escala melhor, se a aplicação não guarda estado local

Sessão, upload temporário e cache em memória precisam de armazenamento compartilhado.

A armadilha

Escalar uma aplicação que espera o banco aumenta a pressão sobre o banco

O sistema fica mais lento, não mais rápido.

Fechamento

  • A ordem: medir, corrigir a consulta, depois cachear
  • Cache: tolerância, invalidação, stampede
  • Fila: backpressure, idempotência, DLQ

  • Cursor no lugar de OFFSET
