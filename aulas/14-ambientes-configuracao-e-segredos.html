Configuração fora do código

Bloco 1 · Tópico 2

Obrigatória ou opcional

const DATABASE_URL = process.env.DATABASE_URL;
if (!DATABASE_URL) {
  throw new Error('Variável obrigatória ausente: DATABASE_URL');
}

const LOG_LEVEL = process.env.LOG_LEVEL ?? 'INFO';

A mesma regra em PHP

$databaseUrl = getenv('DATABASE_URL');
if ($databaseUrl === false || $databaseUrl === '') {
    throw new RuntimeException(
        'Variável obrigatória ausente: DATABASE_URL'
    );
}

$logLevel = getenv('LOG_LEVEL') ?: 'INFO';

Por que falhar cedo

Padrão para algo obrigatório faz a aplicação subir apontando para o lugar errado.

Padrão só serve quando é seguro em qualquer ambiente.

.env.example versionado, com todas as variáveis e nenhum valor real.

Segredos

Bloco 1 · Tópico 3

Nunca no repositório

Nem em commit antigo. Nem em branch esquecida. Nem em log.

O histórico do Git é permanente na prática. Apagar num commit novo não remove nada.

Segredo comitado é segredo comprometido

  1. Revogar e gerar novo
  2. Atualizar os sistemas
  3. Reescrever o histórico

O passo 3 ajuda. Não substitui o passo 1.

Onde guardar, do pior ao melhor

  1. Variável de ambiente do sistema
  2. .env fora do controle de versão
  3. Cofre (Secrets Manager, Vault, cofre do CI)
  4. Credencial de curta duração, sob demanda

Menor privilégio

Bloco 2 · Tópico 4

Saltzer e Schroeder, 1975

Cada componente só com as permissões da sua função.

  • A aplicação conecta com usuário do próprio schema, não superusuário
  • O job de lint não tem escrita no repositório
  • O token que publica imagem não serve para mais nada

A pergunta que dimensiona

Para cada credencial: quem usa, para quê, e o que aconteceria se vazasse.

Se a resposta for “tudo”, ela é grande demais

O GRANT mínimo

CREATE ROLE app_pedidos LOGIN PASSWORD 'trocar-por-gerenciado';

GRANT SELECT, INSERT, UPDATE
  ON pedidos, itens_pedido TO app_pedidos;

REVOKE ALL ON SCHEMA administracao FROM app_pedidos;

Repare no que não está ali: DELETE.

Infraestrutura como código

Bloco 2 · Tópico 5

Em vez de clicar no painel

  • A infraestrutura vira arquivo versionado
  • A revisão acontece antes da mudança, em PR
  • O ambiente pode ser recriado de forma previsível

Um recurso em HCL

resource "aws_db_instance" "pedidos" {
  identifier                  = "pedidos-${var.ambiente}"
  engine                      = "postgres"
  engine_version              = "16"
  instance_class              = var.classe_banco
  allocated_storage           = 20
  publicly_accessible         = false
  manage_master_user_password = true
}

As duas últimas linhas

  • publicly_accessible = false — o banco não recebe conexão da internet
  • manage_master_user_password = true — a senha não aparece no código nem no estado

O arquivo de estado também tem dado sensível: backend remoto, nunca comitado.

GitOps

Bloco 2 · Tópico 6 · Extra

O repositório como fonte da verdade

O estado desejado fica no Git. Um agente reconcilia o cluster com ele.

  • Mudança em produção vira commit aprovado em PR
  • Rollback vira revert
  • Auditoria sai de graça

O preço é disciplina

Alteração feita direto no cluster será desfeita pelo agente.

Isso é desejável — e surpreende quem não conhece o modelo.

Adote quando Git, revisão e pipeline já estiverem consolidados.

Fechamento

  • Paridade: diferença conhecida, pequena e documentada
  • Configuração: obrigatória falha cedo, opcional tem padrão seguro
  • Segredo: comitado é comprometido — revogar primeiro
  • Menor privilégio: se vazar tudo, a credencial era grande demais
  • IaC: infra em PR; o estado é sensível
