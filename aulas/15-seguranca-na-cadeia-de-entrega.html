Vulnerável e seguro em TypeScript

// A entrada vira parte da consulta
db.query(`SELECT * FROM usuarios WHERE email = '${email}'`);

// O driver envia o valor separado da instrução
db.query('SELECT * FROM usuarios WHERE email = $1', [email]);

O mesmo em PHP

// Vulnerável
$pdo->query("SELECT * FROM usuarios WHERE email = '$email'");

// Seguro
$stmt = $pdo->prepare('SELECT * FROM usuarios WHERE email = ?');
$stmt->execute([$email]);

Dois detalhes que pegam

  • ORM não imuniza: SQL cru concatenado dentro dele tem o mesmo problema
  • Identificador não se parametriza: nome de coluna exige lista de permissão
const COLUNAS = ['criado_em', 'total', 'status'] as const;
if (!COLUNAS.includes(coluna)) throw new Error('inválida');

Controle de acesso quebrado

Bloco 1 · Tópico 3

A ferramenta não pega

GET /pedidos/{id} sem verificar o dono: qualquer um lê pedido alheio trocando o número.

O scanner vê uma API devolvendo um recurso por id. Só você sabe a regra.

A defesa é barata

it('usuário B não acessa o pedido do usuário A', async () => {
  const pedido = await criarPedidoComo(usuarioA);
  const resposta = await request(app)
    .get(`/pedidos/${pedido.id}`)
    .set('Authorization', tokenDe(usuarioB));

  expect([403, 404]).toContain(resposta.status);
});

Dependências

Bloco 2 · Tópico 4

O código que você não escreveu

A maior parte da aplicação moderna é dependência de terceiro. Vantagem e superfície de ataque.

  • Lockfile: a versão testada é a implantada
  • Atualizações pequenas e frequentes > salto de seis meses
  • Avalie a necessidade: 300 KB para formatar data?

A suíte é o que permite atualizar

npm audit --omit=dev
composer audit

Se a suíte não é confiável, o problema real não é a atualização.

A pergunta que prioriza

Não é a severidade. É: esse código é alcançável na minha aplicação?

Remoto, não autenticado e sem interação vale mais que dez achados em código nunca executado.

Explorável ou não

Mini desafio 4 · 7 min

  1. Prototype pollution em função que o projeto nunca chama
  2. ReDoS na validação de e-mail, em endpoint público
  3. Falha em dependência de desenvolvimento

Classifique: corrigir já, ciclo normal, ou documentar exceção.

Imagens e SBOM

Bloco 2 · Tópico 5

A base define a superfície

Imagem com compilador, shell e utilitário de rede é mais vulnerável que imagem mínima.

  • Base pequena e mantida
  • Versão fixa, nunca latest
  • Distroless em produção, quando a linguagem permitir

Varredura no pipeline

imagem:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: docker build -t minha-api:${{ github.sha }} .
    - uses: aquasecurity/trivy-action@0.28.0
      with:
        image-ref: minha-api:${{ github.sha }}
        severity: CRITICAL
        exit-code: "1"

Comece pelo grave

Pipeline vermelho no primeiro dia vira job desabilitado na semana seguinte

SBOM: a lista completa de componentes. Quando sair a próxima vulnerabilidade crítica, você responde em minutos quais serviços são afetados.

Auditoria da cadeia de uma API

Desafio integrador · 45 min

Em dupla

Quatro partes

  1. Modelagem de ameaças de uma página, com três ameaças e mitigações
  2. Análise de dependências: para cada achado alto, é explorável aqui? Por quê?
  3. Scanner de imagem no pipeline, falhando em crítico
  4. Teste de autorização entre dois usuários

Verificação

Verificação Saída esperada
Consulta parametrizada Nenhuma concatenação de entrada em SQL
Autorização entre dois usuários B no recurso de A retorna 403 ou 404
Scanner no pipeline Vermelho com crítico, ou verde sem nenhum

Exceção documentada precisa de justificativa escrita e data de revisão.

Fechamento

  • Modelagem: uma folha, quatro perguntas, revisada quando muda
  • Injeção: parametrizar; ORM não imuniza
  • Autorização: ferramenta não pega — o teste pega
  • Dependências: alcançabilidade antes de severidade
  • Imagem: base mínima, versão fixa, SBOM

Dever de casa

  2. Teste de autorização entre dois usuários, verde no repositório
  3. Classificar cada achado alto como explorável ou não, com justificativa
