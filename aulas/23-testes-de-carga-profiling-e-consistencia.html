Tipos de teste de carga

Quatro perguntas diferentes

Tipo Pergunta que responde

O erro mais comum

Rodar um teste de carga de dois minutos e declarar que o sistema aguenta.

Ele não revela nada sobre estabilidade ao longo do tempo

No estresse, o modo de falha importa tanto quanto o número: degrada com elegância, ou cai de uma vez?

Um teste com k6

Bloco 1 · Tópico 2

Cenário em JavaScript

export const options = {
  stages: [
    { duration: "2m", target: 200 },
    { duration: "10m", target: 200 },
    { duration: "1m", target: 0 },
  ],
  thresholds: {
    http_req_duration: ["p(95)<300"],
    http_req_failed: ["rate<0.01"],
  },
};

export default function () {
  const res = http.get("http://api:8000/catalogo");
  check(res, { "status 200": (r) => r.status === 200 });
  sleep(1);
}

Dois detalhes que mudam o resultado

  • A subida gradual evita medir o cold start — pool vazio, cache frio
  • O sleep(1) simula um usuário real

Sem sleep, o teste roda em laço fechado e mede o throughput máximo, não o uso real.

Escreva o cenário

Mini desafio 2 · 7 min

A busca precisa suportar 200 usuários simultâneos, com p95 < 300 ms e falha abaixo de 1%.

Thresholds como quality gate

Bloco 1 · Tópico 3

Critério objetivo

Se o p95 passar de 200 ms ou a falha passar de 1%, o k6 termina com erro e o pipeline falha.

É o mesmo padrão da cobertura (M2) e do scanner de imagem (M3), agora em desempenho.

O viés que invalida tudo

Um teste numa máquina local com o banco na mesma máquina mede a máquina, não o sistema

Registre sempre as características do ambiente.

E o threshold vem de onde?

Do alvo de negócio — não da medição.

Threshold definido depois de medir (“deu 180, ponho 200”) sempre passa, e portanto nunca protege ninguém.

O resultado vale?

Mini desafio 3 · 5 min

“A API suporta 500 usuários simultâneos com p95 de 180 ms. Teste de 10 minutos com k6.”

Profiling

Bloco 2 · Tópico 4

Onde o tempo é gasto no processo

node --cpu-prof app.js
python -m cProfile -s cumtime app.py > perfil.txt

O profiler responde “onde”, não “por quê”.

O detalhe que engana

Tempo de espera por I/O não aparece como consumo de CPU

O profiler mostra a aplicação “ociosa” mesmo quando ela está lenta por espera.

Profiler para gargalo de CPU. Trace para gargalo de espera.

CAP e PACELC

Bloco 2 · Tópico 5

CAP, com a letra miúda

Durante uma partição de rede, escolha entre consistência e disponibilidade.

Partições são raras, mas inevitáveis. E a escolha vale só durante a falha.

PACELC completa

Partição → escolha entre A e C.

Else → mesmo sem falha, escolha entre Latência e Consistência.

O segundo é o que afeta o dia a dia: replicação síncrona dá consistência ao custo de latência em toda escrita.

A decisão é de negócio

Decisão Pergunta Escolha
Saldo de pontos no perfil Pode estar segundos atrás? Sim Latência
Disponibilidade no pagamento Pode vender o que acabou? Não Consistência
Contagem de avaliações Pode errar por um minuto? Sim Latência

As três convivem no mesmo sistema. PACELC classifica a decisão, não a marca do banco.

IA para hipóteses de gargalo

Bloco 2 · Tópico 6 · Extra

Hipótese, não diagnóstico

Curva de latência que sobe com as conexões sugere esgotamento de pool. Que sobe com o tamanho da resposta sugere serialização.

Mesmo método do E18: fato, hipótese, teste.

A nota que fecha o curso

Aumentar limites costuma mover o gargalo, não eliminá-lo

Pool, threads, memória. Meça o efeito de cada mudança isoladamente.

Mover ou eliminar

Mini desafio 6 · 7 min

A IA sugeriu aumentar o pool de 10 para 50. O p95 caiu de 1,2 s para 900 ms — e voltou a subir com mais usuários.

A sugestão foi boa? O que aconteceu com o gargalo?
