Aula 4 — Engenharia Limpa

Full Cycle · Módulo 1 — Engenharia de Software e IA Aplicada

Objetivo de aprendizagem

Ao final desta aula, você deve ser capaz de:

  • Escrever código com nomes reveladores de intenção e funções pequenas
  • Identificar code smells e aplicar técnicas de refatoração
  • Justificar decisões de design usando os princípios SOLID
  • Situar essas práticas dentro da Clean Architecture

Nomes significativos e funções pequenas

  • Nomes significativos: um bom nome dispensa comentário explicativo
    • diasDesdeAUltimaModificacao em vez de int d
  • Funções pequenas (Do One Thing):
    • Nível único de abstração
    • Sem argumentos flag (true/false indicando que a função faz duas coisas)
    • Poucos parâmetros (0–2; 3+ vira um objeto de contexto)

Tratamento de erros e melhoria contínua

  • Tratamento de erros: evitar return null (obriga checagens em cascata); preferir exceções explícitas ou Optional
  • Regra do Escoteiro: “deixe o código mais limpo do que encontrou” — melhoria incremental a cada commit, não reescrita total
  • Ciclo TDD + Clean Code:

RED (teste que falha) → GREEN (código mínimo que passa) → REFACTOR (limpar sem quebrar o teste verde)

Code smells

Não são bugs, mas sintomas de arquitetura ruim:

  • Long Method / Large Class
  • Feature Envy — método que mexe mais nos dados de outra classe do que na própria
  • Data Clumps — grupos de variáveis que sempre andam juntas e deveriam virar uma classe
    • ex.: rua, numero, cep, cidade → Endereco

Técnicas de refatoração

  • Extract Method / Class: transformar um trecho comentado (“aqui calcula o total”) em uma função com esse nome
  • Substituir condicionais por polimorfismo: trocar switch/if-else de tipo pelo padrão Strategy (interface + implementações)

Regra de ouro: refatorar muda a estrutura sem alterar o comportamento externo; nunca refatorar código sem testes.

SOLID — S e O

  • S — Single Responsibility: uma classe, um motivo para mudar
    • ex.: separar RelatorioRepository de PDFReportGenerator
  • O — Open/Closed: aberto para extensão, fechado para modificação
    • analogia da tomada elétrica

SOLID — L, I e D

  • L — Liskov Substitution: subclasse deve substituir a classe-mãe sem quebrar o sistema
    • ex.: Pinguim que herda de Ave e não consegue voar() quebra o LSP
  • I — Interface Segregation: várias interfaces específicas em vez de uma gigante com métodos vazios
  • D — Dependency Inversion: módulos de alto nível dependem de abstrações (interfaces), não de implementações concretas — injeção de dependência por construtor

Clean Architecture (Robert C. Martin)

Objetivo: isolar a regra de negócio de detalhes tecnológicos mutáveis (banco, framework web, UI) — tratados como “plug-ins” substituíveis.

Camadas concêntricas (de dentro para fora):

Entities (regras de negócio puras) → Use Cases (orquestram o fluxo) → Interface Adapters (controllers, presenters, repositories) → Frameworks & Drivers (Spring, Express, MySQL, AWS SDKs)

Regra de dependência

O código de uma camada interna nunca cita nada de uma camada mais externa — dependências sempre apontam para dentro.

Atividade prática sugerida

  1. Pegar um trecho de código “sujo” (fornecido ou de um projeto próprio)
  2. Identificar 2–3 code smells
  3. Refatorar aplicando Extract Method e pelo menos um princípio SOLID
  4. Manter os testes verdes

💻 Exemplo prático guiado

Refatorando o Diário de Café.

❌ Antes: uma classe “deus” (viola SRP e OCP)

class ReceitaService {
  executarReceita(nome: string, tipoMetodo: string, dose: number, protocolo: string, avaliacao: any) {
    let agua;
    if (tipoMetodo === "v60") agua = dose * 16;
    else if (tipoMetodo === "aeropress") agua = dose * 14;
    else if (tipoMetodo === "prensa") agua = dose * 12;

❌ Antes (continuação)

    let nota;
    if (protocolo === "sca") {
      nota = avaliacao.fragancia + avaliacao.sabor + avaliacao.acidez + avaliacao.corpo + avaliacao.docura - avaliacao.defeitos;
    } else {
      nota = (avaliacao.fragancia + avaliacao.sabor * 2 + avaliacao.acidez + avaliacao.corpo + avaliacao.docura) / 1.2;
    }

    console.log(`Receita ${nome} preparada com ${agua}ml de agua`);
    // salva no banco...
    // envia notificacao por email...
    return nota;
  }
}

Problemas identificados

A função calcula proporção de água, pontua o cupping, loga, salva e notifica — cinco motivos diferentes para mudar (viola SRP).

Cada novo método de extração ou protocolo de pontuação exige editar essa mesma função (viola OCP).

✅ Depois: SOLID + Clean Architecture

Reaproveitando as classes da Aula 3.

Entities (regra de negócio pura, sem dependência de framework): MetodoExtracao, Receita, ProtocoloDePontuacao — já prontas.

Use Case (orquestra o fluxo, depende só de abstrações — DIP):

interface ReceitaRepository {
  salvar(receita: Receita): Promise<void>;
}
interface Notificador {
  avisar(mensagem: string): Promise<void>;
}

Use Case

class ExecutarReceitaUseCase {
  constructor(
    private repository: ReceitaRepository,
    private notificador: Notificador
  ) {}

  async executar(receita: Receita): Promise<string> {
    const instrucao = receita.executar();
    await this.repository.salvar(receita);
    await this.notificador.avisar(`Receita executada: ${instrucao}`);
    return instrucao;
  }
}

Interface Adapters

Implementações concretas, substituíveis como plug-ins:

class ReceitaRepositoryPostgres implements ReceitaRepository {
  async salvar(receita: Receita): Promise<void> { /* INSERT no Postgres */ }
}
class NotificadorEmail implements Notificador {
  async avisar(mensagem: string): Promise<void> { /* envia e-mail */ }
}

Frameworks & Drivers: Express (rota HTTP) + driver pg do Postgres, na camada mais externa.

O que mudou

  • Cada classe agora tem um único motivo para mudar (SRP)
  • Adicionar um novo método de extração ou protocolo de pontuação não toca mais o ExecutarReceitaUseCase (OCP)
  • Trocar Postgres por outro banco, ou e-mail por push notification, só exige uma nova classe de Adapter — o Use Case nem percebe (DIP)
