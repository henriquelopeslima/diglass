Prompts técnicos

Anatomia de um bom prompt

  1. Papel: quem a IA deve ser
  2. Contexto: domínio, regras, volume, equipe, prazo
  3. Tarefa: o que você quer
  4. Restrições: o que não pode
  5. Formato: como responder

Prompt ruim, prompt bom

faz um repository pra mim
Papel: dev backend sênior em PHP.
Contexto: pedidos de e-commerce, 3 devs, SQLite.
Tarefa: salvar Order sem acoplar o domínio ao banco.
Restrições: sem framework; testável sem banco.
Peça: 3 alternativas com prós, contras e quando NÃO usar.

Contexto muda a resposta

Informe Porque
Volume de dados Define se precisa escalar
Equipe e prazo Define a complexidade aceitável
Regras de negócio Define o modelo
Restrições Evita a solução “bonita” impossível

Itere e peça o contraditório

  • Peça alternativas, e não “a melhor”
  • Peça os riscos e quando não usar
  • Pergunte: “o que você não sabe sobre o meu contexto?”
  • A segunda pergunta vale mais que a primeira

Active Record vs Repository

Active Record

final class OrderRecord
{
    public function save(): void { /* INSERT OR REPLACE ... */ }

    public static function find(PDO $db, string $id): ?self
    {
        /* SELECT ... WHERE id = :id */
    }
}

O objeto conhece o banco. Simples e rápido para CRUD.

Repository

interface OrderRepository
{
    public function save(Order $order): void;

    public function find(string $id): ?Order;
}

O domínio pede e recebe entidades. O armazenamento fica escondido.

Data Mapper

Order (entidade)  ◄──►  OrderMapper  ◄──►  linha da tabela
  não sabe do banco      converte           id | total | status
  • A entidade não conhece SQL
  • O mapper faz toRow() e fromRow()
  • O repositório usa o mapper

Testar sem banco

$mem = new InMemoryOrderRepository();
$mem->save(new Order('R2', 50.0));

echo (new PayOrder($mem))->run('R2');   // paid

Com Repository, o teste roda sem banco. Com Active Record, precisa de banco.

Como escolher

Active Record Repository + Mapper
Classes Poucas Mais
Regras de negócio Simples Complexas
Teste sem banco Difícil Fácil
Bom para CRUD Domínio rico

Transaction Script e CQRS

Transaction Script

$db->beginTransaction();
try {
    baixarEstoque($db, $sku, $qty);   // lança se faltar
    gravarPedido($db, $id, $total);
    $db->commit();
} catch (Throwable $e) {
    $db->rollBack();
    throw $e;
}

Um caso de uso, um procedimento, uma transação.

Quando o script deixa de servir

  • A mesma regra aparece em vários scripts
  • Os if viram uma teia
  • Ninguém sabe onde está a regra

Aí o modelo de domínio (Repository) compensa.

CQRS

COMANDO  ──►  escreve  orders  ──►  atualiza  daily_sales
                                              ▲
CONSULTA ─────────────────────────────────────┘  só lê

Separa escrever de ler. A leitura tem um modelo próprio.

O custo do CQRS

  • Duas vias para manter
  • A leitura pode ficar atrasada (consistência eventual)
  • Sem o problema de escala, é overengineering

2 mil pedidos por dia? Provavelmente não.

Decidindo com IA

O fluxo da decisão

Problema → Prompt com contexto → IA sugere alternativas
   → VOCÊ valida → Decisão humana → Registro

Se não entendeu, testou e validou, volte ao prompt.

Registro de decisão

## Contexto
O problema e as restrições.

## Alternativas (sugeridas pela IA)
A, B e C, com prós e contras.

## Decisão
Escolhemos B, porque...

## Riscos
O que pode dar errado.

Quando a IA está errada

  • “Use X em tudo”: conclusão genérica
  • SQL por concatenação de texto
  • Esquece a transação
  • Sugere uma escala que você não tem

Avise no PR quando o código veio de IA e o que você validou.
