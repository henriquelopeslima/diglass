O que são Design Patterns

Pattern é…

  • Uma solução recorrente para um problema recorrente
  • Um nome para a equipe se entender
  • Uma ideia, e não código pronto

Não é framework, biblioteca nem regra obrigatória.

Três famílias

Família Pergunta Exemplos
Criação Como criar objetos? Factory, Builder, Singleton
Estruturais Como compor objetos? Adapter, Decorator, Facade
Comportamentais Como colaboram? Strategy, Observer, Command

Princípio primeiro, pattern depois

Princípio (o quê) Pattern (como)
O Open/Closed Strategy, Decorator
D Dependency Inversion Adapter, Factory
S Single Responsibility Decorator, Facade

Pattern é uma forma concreta de aplicar um princípio.

Quando usar, quando evitar

Comece pela dor, não pelo catálogo.

  • Use se o problema se repete e a solução simples já não serve
  • Evite se o problema é pequeno ou ainda não doeu

Strategy

O problema

if ($customer === 'vip') {
    $total *= 0.8;
} elseif ($total > 100) {
    $total *= 0.9;
} elseif ($coupon === 'PROMO') {
    $total -= 20;
}

Toda regra nova edita esse if. E ele está no checkout.

Strategy: o contrato

interface DiscountStrategy
{
    public function apply(float $subtotal): float;
}

Uma classe por regra: NoDiscount, PercentDiscount(10), FixedDiscount(20).

Strategy: uma regra

final class PercentDiscount implements DiscountStrategy
{
    public function __construct(private float $percent) {}

    public function apply(float $s): float
    {
        return $s - $s * $this->percent / 100;
    }
}

Strategy: quem usa

$service = new CheckoutService(
    new PercentDiscount(10),   // troque a regra aqui
    new Pix(), $repository, $notifier,
);

Nova regra = classe nova. O CheckoutService não muda.

Strategy · TypeScript

interface DiscountStrategy {
  apply(subtotal: number): number;
}

class PercentDiscount implements DiscountStrategy {
  private percent: number;
  constructor(percent: number) { this.percent = percent; }

  apply(subtotal: number): number {
    return subtotal - (subtotal * this.percent) / 100;
  }
}

Mini desafio · Estratégias de desconto

  1. Crie DiscountStrategy
  2. Implemente 3 regras: nenhuma, percentual e fixa
  3. Rode 120 por cada uma

Extra: o desconto fixo nunca deixa o total negativo.

Factory

O problema

if ($type === 'pix') { $method = new Pix(); }
elseif ($type === 'card') { $method = new Card(); }
elseif ($type === 'boleto') { $method = new Boleto(); }

Esse trecho existe em 5 lugares. O Boleto entrou: 5 edições.

Factory

final class PaymentFactory
{
    public static function make(string $type): PaymentMethod
    {
        return match ($type) {
            'pix' => new Pix(),
            'card' => new Card(),
            default => throw new InvalidArgumentException($type),
        };
    }
}

Factory: cuidados

  • O match cresce a cada tipo novo
  • Um registro de criadores mantém o Open/Closed
  • Chame a fábrica na borda (controller), e não dentro do serviço

O serviço continua recebendo o objeto pronto.

Mini desafio · Uma fábrica de pagamentos

  1. Crie PaymentFactory::make(type)
  2. Aceite pix, card e boleto
  3. Tipo desconhecido lança erro

Extra: troque o match por um registro.

Decorator

O problema

Queremos log, prefixo e retry no Notifier.

LoggingEmailNotifier      LoggingSmsNotifier
PrefixLoggingEmailNotifier   RetryLoggingSmsNotifier

Cada combinação vira uma classe.

Decorator

final class LoggingNotifier implements Notifier
{
    public function __construct(private Notifier $inner) {}

    public function notify(string $message): void
    {
        error_log("enviando: {$message}");
        $this->inner->notify($message);
    }
}

Empilhando

$notifier = new LoggingNotifier(
    new PrefixNotifier(new EmailNotifier(), '[PEDIDOS] ')
);
  • Mesma interface por dentro e por fora
  • A ordem das camadas importa
  • Combina em execução, e não em tempo de escrita

Mini desafio · Notificações com camadas

  1. Crie LoggingNotifier e PrefixNotifier
  2. Empilhe sobre o EmailNotifier
  3. Mostre o log e a mensagem final

Extra: inverta a ordem. O que muda?

Adapter e Facade

O problema do SDK

// Biblioteca externa: não podemos editar
$client->createCharge(int $amountInCents, string $currency);

O nosso contrato é PaymentMethod::pay(float $amount).

Espalhar o SDK pelo sistema prende tudo a ele.

Adapter

final class AcmePayAdapter implements PaymentMethod
{
    public function __construct(private AcmePayClient $client) {}

    public function pay(float $amount): string
    {
        $cents = (int) round($amount * 100);
        $c = $this->client->createCharge($cents, 'brl');
        return "AcmePay {$c['id']}";
    }
}

Facade

final class PlaceOrderFacade
{
    public function place(string $id): array
    {
        return [
            $this->inventory->reserve($id),
            $this->billing->charge($id),
            $this->shipping->schedule($id),
        ];
    }
}

Adapter vs Facade

Adapter Facade
Faz Converte interfaces Simplifica o uso
Esconde Um SDK ou classe Um subsistema inteiro
Princípio D S

Trocou o fornecedor? Muda um arquivo: o adapter.

Mini desafio · Adapte o gateway

  1. Use o AcmePayClient sem editá-lo
  2. Crie AcmePayAdapter implements PaymentMethod
  3. Pague 108 e mostre o resultado

Extra: e se o SDK trocasse brl por BRL?

Observer e como escolher

O problema

O checkout chama e-mail, estoque e analytics diretamente.

  • Cada novo interessado edita o checkout
  • O checkout conhece todo mundo
  • Falha em um derruba o fluxo

Observer

interface OrderListener
{
    public function onOrderPlaced(string $id, float $total): void;
}

$events->subscribe(new SendEmail());
$events->subscribe(new UpdateStock());
$events->dispatch('A1', 108);   // avisa todos

Singleton, com ressalvas

  • Garante uma instância global
  • Mas cria estado global e dificulta os testes
  • Prefira uma instância injetada a Config::instance()

Pergunte antes: preciso mesmo de uma só?

Como escolher

Sintoma Pattern
